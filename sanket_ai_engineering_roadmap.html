Sanket's AI Engineering practical roadmap — 4 phases, 7 standalone projects, mapped to book chapters

NyayaSathi is completely separate. Every project below is standalone, fresh codebase, different domain.
Phase 1 — Start here · 2–3 weeks The foundation project
Project 1 — AI Study Buddy (CLI)
A command-line tool where you type a topic, it generates explanation + quiz + follow-up questions using raw Gemini/OpenAI API calls. No frameworks. Pure Python.
LLM basics Generation params Text generation strategies Prompt engineering JSON prompting CoT prompting
Build in this exact order:
1. Call Gemini API, get a plain text explanation of any topic
2. Add temperature, top_p, max_tokens controls — see how output changes
3. Force JSON output (structured quiz: question + 4 options + answer)
4. Add chain-of-thought: "think step by step before answering"
5. Add greedy vs sampling vs beam comparison — show 3 outputs for same prompt

Why this first: You learn LLM behavior directly. No abstraction layer hiding what's happening. Every AI project you build after this will be clearer because you understand generation fundamentals.

Phase 1 continued · week 3–4 Add memory and evaluation to Project 1
Project 2 — Upgrade Study Buddy to a stateful tutor
Same project, now with conversation history, session memory, and a self-evaluation loop. The LLM grades its own previous answer using G-eval logic.
LLM memory types Multi-turn conversation G-eval Component-level evals LLM-as-judge
1. Add conversation history array — pass full history each API call
2. Add in-memory session store (Python dict, not Redis — keep it simple)
3. After each explanation, call the LLM again with: "Rate this explanation 1–5 for accuracy, clarity, completeness. Return JSON."
4. Log every score. Show running average.
5. If score is below 3, auto-regenerate with a better prompt.

Why this is the same project: Upgrading existing code is realistic. You see concretely how evaluation plugs into generation, not as a separate concern.
↓
Phase 2 · weeks 5–7 Build your first real Agent — completely new project
Project 3 — News Research Agent
An agent that takes a research question, autonomously decides which tools to call (web search, summarizer, fact-checker), reasons step by step, and produces a structured report. Built from scratch — no LangChain.
ReAct pattern Tool use Agent loop Agent memory Agentic design patterns Context engineering Verbalized sampling
Build in this order:
1. Write the ReAct loop manually: Thought → Action → Observation → repeat
2. Define 3 tools as Python functions: web_search(), summarize_text(), check_claim()
3. Build the tool-calling parser: LLM outputs "Action: web_search(query)" → your code parses and executes
4. Add working memory: agent keeps a scratchpad of observations so far
5. Add context window management: trim old observations when context gets too long
6. Final output: structured JSON report with sources

Why this domain (news): You can test it immediately, it's verifiable, and recruiters understand it instantly when you demo it.
↓
Phase 2 continued · weeks 7–9 Add RAG to the Agent — new knowledge source
Project 4 — Research Agent + personal knowledge base
Extend Project 3. The agent now has a 4th tool: a local RAG pipeline over a folder of PDFs/notes. You build the chunking, embedding, and retrieval from scratch using ChromaDB (not Pinecone — keep it local and simple).
RAG from scratch 5 chunking strategies Vector DB (ChromaDB) HyDE RAG vs Agentic RAG Prompting vs RAG vs FT
1. Implement chunking: try fixed-size, sentence-based, semantic — compare retrieval quality
2. Embed with Gemini embedding-001, store in ChromaDB locally
3. Add as a tool: knowledge_base_search(query) → returns top-3 chunks
4. Implement HyDE: generate a hypothetical answer first, embed that, then retrieve
5. Compare: direct query retrieval vs HyDE retrieval — log which gives better chunks
6. The agent now decides: should I search web or search knowledge base?

This is where RAG stops being a standalone thing and becomes one capability inside an intelligent system.
↓
Phase 3 · weeks 9–11 Expose your Agent as a service — MCP + Observability
Project 5 — Wrap Project 4 as an MCP server with full tracing
Take the Research Agent you built. Wrap it as an MCP server so Claude Desktop (or any MCP client) can call it. Add Opik or LangSmith tracing so every LLM call, tool call, and retrieval is logged and visible.
MCP architecture MCP tools/resources/prompts MCP server creation LLM Observability Eval vs Observability Multi-turn evals
1. Install MCP Python SDK, expose 3 MCP tools: research(question), add_to_kb(pdf_path), get_report(topic)
2. Connect to Claude Desktop — test calling your agent from Claude's UI
3. Instrument with Opik: every LLM call gets a trace with input, output, latency, cost
4. Add eval spans: log retrieval quality score, agent step count, final answer score
5. Build a simple dashboard showing: avg steps per query, avg score, failure rate

After this you can say: "I built an MCP server and instrumented it with observability." That's a strong portfolio statement.

Phase 4 · weeks 12–15 Multi-agent system — completely new project
Project 6 — AI Code Review System (multi-agent)
A new project entirely. You submit a GitHub PR link. An orchestrator agent spawns 3 sub-agents: one reviews logic, one checks security, one checks style. They report back. Orchestrator synthesizes a final review. Uses A2A communication pattern.
Multi-agent patterns Orchestrator pattern A2A protocol 5 levels of agentic AI Agent deployment Red teaming LLM apps
1. Orchestrator: receives PR diff, decides which specialist agents to invoke
2. Agent 1 (Logic): reads code, identifies bugs, returns structured JSON findings
3. Agent 2 (Security): checks for hardcoded secrets, SQL injection, common vulns
4. Agent 3 (Style): checks naming, complexity, documentation
5. Orchestrator synthesizes all 3 reports into one final review
6. Red team it: try to make it miss a bug, hallucinate a problem, loop infinitely
7. Deploy as a FastAPI endpoint

Why code review: You already know code, so you can verify if the agent is right or wrong. That makes debugging much faster.
↓
Phase 4 continued · weeks 15–18 Fine-tuning — only now, not before
Project 7 — LoRA fine-tune a small model for code review
Fine-tune Mistral-7B or Phi-3 using LoRA on a dataset of good code reviews. Compare: base model vs fine-tuned model on your Project 6 test cases. You now know what "better" means because you already built the evaluator in Phase 2.
Fine-tuning concepts LoRA from scratch IFT dataset generation SFT vs RFT Full FT vs LoRA vs RAG
1. Generate IFT dataset: use GPT-4 or Claude to generate 500 (code, review) pairs
2. Fine-tune Phi-3-mini with LoRA on Google Colab (free T4 is enough for Phi-3)
3. Run your evaluation harness from Project 2 on: base model vs fine-tuned
4. Document: where does FT help? Where does RAG beat FT? Where does prompting win?
5. Write a short "what I learned" that you can paste into your LinkedIn post

Why last: Fine-tuning without an evaluator is blind. You now have 6 projects of evaluation experience. You'll actually understand the results.
What this roadmap deliberately skips (and why)
LLM from scratch training — not needed for any entry-level role you're targeting
GRPO / SFT / RL training — only after you have GPU budget and a clear use case
KV cache / quantization internals — Defer until a job requires it
vLLM / LitServe deployment — Phase 5 if you want, after you're placed
AG-UI protocol — very new, reference-only for now
